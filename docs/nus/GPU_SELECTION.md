# GPU 选型规范（实测基准，2026-11-12）

状态：**当前**。给后续 Agent 用：**选 GPU 时按"有效训练量 / 墙钟小时"决策，不要凭型号偏好，
也不要只为了避免排队而降级硬件。**

---

## 1. 结论先行

**优先用 H100（`h100-47` / `h100-96`），不要退到 `nv`。**
H100 每个运行分钟产出约 **3.3 倍**的决策量、约 **6 倍**的迭代数，即使加上 6 分钟的排队，
按墙钟时间算仍然快 **2.7 倍**。

**不要钉死 GPU 型号**（钉 `h100-47` 曾导致 2 小时 15 分的排队），但也**不要为了即排即跑
落到 `nv`**——那是拿 3 倍算力换 6 分钟。

---

## 2. 实测条件（保证可比）

| 项 | 值 |
|---|---|
| 配置 | `config/league-stage2.json`（完全相同） |
| 局数 / 段长 | **512 局 / 8 分钟**（完全相同） |
| 进程 | 8（`--processes 8`，workers 在 cuda:1，trainer 在 cuda:0） |
| 卡数 | **2 张同型号**（trainer state 存了两张卡的 CUDA RNG，1 卡无法续训） |
| 起点 | `league-final-20261111-step014858`（同一个 fork） |
| 段数 | 1（单段，不受"代码已变更"守卫影响） |
| 指标 | `collect.decisions_per_s` 与迭代数，取自各自 `train/history.jsonl` |

## 3. 实测结果

| GPU | 节点 | 排队 | 实际用时 | 迭代数 | decisions/s | **每次运行分钟的迭代数** |
|---|---|---:|---:|---:|---:|---:|
| **h100-47×2** | xgpi11 | **6.2 min** | 13:47 | **18** | **6,691** | **≈1.3** |
| nv×2 | xgpd0 | 0.2 min | 08:39 | 3 | 2,005 | ≈0.35 |

**折算到墙钟小时**（含排队）：

| GPU | 每小时迭代数 | 相对 |
|---|---:|---:|
| h100-47×2 | 18 ÷ 19.9 min × 60 ≈ **54** | **2.7×** |
| nv×2 | 3 ÷ 8.8 min × 60 ≈ **20** | 1.0× |

> 也就是说：**同一段墙钟时间，H100 能做 2.7 倍的训练量**，即便它多等了 6 分钟。

## 5. 调度硬约束（踩过的坑）

1. **`QOSMaxGRESPerUser`**：同时能持有的 2 卡作业有上限。一次提交 5 个 2 卡作业会有 2 个
   卡在 `QOSMaxGRESPerUser`。**基准测试必须串行提交。**
2. **不要钉死型号**：`--gres=gpu:h100-47:2` 曾排队 2h15m；`--gres=gpu:2` 立刻开跑。
3. **但 `--gres=gpu:2` 可能给到 `nv`**：要性能就得指定 `h100-*`，要立刻开跑就得接受降级。
   两者不可兼得时，**按第 1 节的墙钟效率算，选 H100**。
4. **续训必须 2 张同型卡**：trainer state 里的 `cuda_rng` 是 2 项，1 卡恢复会越界。
5. **部分节点的卡可能只分到 1 张**：请求 2 张不等于拿到 2 张，日志里会出现
   `actor GPU 越过当前可见设备范围 0..0`。

## 6. 选型流程（给后续 Agent）

```
1. squeue -u $USER                    # 先看自己有没有占着 GRES（QOS 上限）
2. sinfo -h -p gpu -o '%N|%G|%t|%C'   # 找 h100-* 且 CPU 空闲多的节点
3. 提交时 --gres=gpu:h100-47:2 或 h100-96:2（不要写死单一型号，二者都试）
4. 若两者都排 >20 分钟，再考虑 a100-*（需确认节点真有 >=2 张同型号卡）
5. 只有在"必须在 10 分钟内拿到结果"时才用 nv，并明确记录这是降级
```
