## 5.4 一个必须先说清的尺度问题（2026-11-13 05:40）

至今所有臂都是 **6 段 × 20 min ≈ 100–210 轮**的微实验，而 champion
`league-final-14858` 来自 **36 小时联赛、5,316 条 history**。也就是说：

> 用 2 小时的 fork 去"显著超过"一个 36 小时的同源模型，本来就不现实。

**微实验的用途只能是"筛配方"，不是"出成果"**。因此流程应当是：

1. 用这批微实验（D1 的 6k 战团库、G5c/G6c/G7 的门控等级奖励、F4c 的 6k 入场库）
   筛出**唯一一条**最不坏的配方组合；
2. 然后用它开一次**长训**（≥ 12 h，`HSAI_LE_SEGMENTS=36 HSAI_LE_MINUTES=20`
   或 `24×60`），跑满再判；
3. 长训期间只做**评测侧**改动（`workflows/eval_human_gap.py`、`tools/`），
   绝不碰 digest。

这条也解释了为什么"D1 名次不掉"值得重视：它是唯一一个**没有把 champion 变差**的
fork，正是长训的合适起点。

**长训的确切命令模板**（`gpu` 分区 MaxTime 只有 3 h，12 h 必须走 `gpu-long`，
命令行覆盖 sbatch 头里的 partition/time）：

```bash
# 注意：--export 的值必须写在一行里（不能折行、不能用 shell 变量，见 D-038）
sbatch --partition=gpu-long --gres=gpu:h100-47:1 --cpus-per-task=32 --mem=96G --time=12:00:00 --export=ALL,HSAI_LE_OUT=artifacts/runs/entry-main-YYYYMMDD,HSAI_LE_CONFIG=config/league-entry-RECIPE.json,HSAI_LE_SEGMENTS=36,HSAI_LE_MINUTES=20 deploy/slurm/late_entry.sbatch
```

36 段 × 20 min = 12 h，段间自动 `--resume`；**期间禁止任何 digest 相关推送**（D-037）。

## 5.18 决定性负结果：用我们现有 BC 样本做 BC 初始化会把 champion 推坏（13:26）

**为什么做这个实验**：群友模型是 **BC 初始化 → PPO** 的成功案例，而我们所有 fork 都是纯 PPO。
这是流程上最大的不对称，所以用我们自己的样本池做一次受控实验（`1129252`，10 分钟跑完）：
champion 起点、`mmr-min 6000`、`lr 3e-5`、4 epoch、`anchor-beta 0.05`。

**结果（真人场 96 局，配对 bootstrap）**

| 指标 | base(champion) | **bc1** |
|---|---:|---:|
| mean_rank | **5.4375** | **7.4896**（Δ=+2.05，CI **[1.68, 2.43]**） |
| 前四率 | 0.323 | **0.042** |
| T10 板面 | 1.000 | **0.674**（−33%） |
| 前期 T2–T7 | — | **−20%~−51%** |
| ≥1 S 覆盖 | 0.138 | 0.231（略高，但只有 13 局活到统计回合） |

BC 自己报告 `holdout_type_acc 0.462`、**`kl_mean 2.29`（> 告警线 2.0）**——策略确实学了很多，
但学的是**错的状态分布**。

**根因（与代码一致）**：我们的 BC 样本（`bc_samples.jsonl.gz`）只有
`turn/gold/tier/health/board/hand/shop/hero` 等字段，`bc_aux.bc_obs_batch()` 会**把未知槽位全部置 0**
并置 `feature_mask=False`——也就是 BC 看到的是**部分观测**（对手、任务、英雄技能、饰品、
关键词/counters 全是 0），而 PPO/实战看到的是完整 3227 维。**训练分布与使用分布不一致**，
所以"人类动作先验"没有迁移，只带来了灾难性遗忘。

**结论**：**群友的 BC→PPO 配方在我们身上不可直接复制**——不是 BC 错了，是我们的 **BC 数据不够**。
要让 BC 可用，必须先有"**完整观测 + 人类动作**"的样本流（需要把 Firestone 回放在我们的引擎里
重放到决策点、再取当时的完整 obs），这是**数据工程**，不是调参。

**因此路线调整**：P1 关闭；优先做 P2（流派条件化）与 P3（keep-start-board 掩码），
两者都不依赖 BC 数据质量。

## 5.33 备好 `S1`：**势函数式**成长塑形（`shaping-mode log_strength`）

§5.32 说差距是"成长速率"（人类 T10→T12 每格 ×5.3/2 回合，模型 ×1.7/2 回合）。
但此前所有"加板面奖励"都失败了（Σ 口径、`board-target`、`terminal-strength`），
因为它们奖励的是**水平**（level），可被"就地买厚"满足，且不满足最优策略不变性。

仓库里其实早有一个**理论上不可打穿**的机制：`--shaping-coef λ --shaping-mode log_strength`
（`hsbg/az/train/ppo.py`）。它是**势函数式**塑形：

```
F_t = λ·(γ·Φ(s_{t+1}) − Φ(s_t)),  Φ = L(Σ) = log(1+Σ)
γ_s == 训练 γ（=1.0）时整局望远镜求和 = λ·(L(Σ_T) − L(Σ_0))，
```

即**整局奖励与策略无关**（Ng et al. 1999 意义下的 policy invariance）——它只重新分配
"哪一步对最终变强有贡献"的信用，**不改变最优策略**，因此不存在"刷分"路径。

`config/league-entry-s1.json` = **M1 + `shaping-coef 0.1` + `shaping-mode log_strength` +
`shaping-gamma 1.0`**（其余逐字段相同）。`λ=0.1` 的量级：Σ 从 300 长到 1500 时
整局塑形项 ≈ 0.16，与名次效用（±1）同量级但更小——目标是**锐化信用分配**，不是替换名次。

**启动条件**：先看 M0/M1 在 19:05（约 45–90 轮）的读数。
若 M1 的 `tier`/`upgrade` 开始动 → 继续 M1 链；若不动 → 停掉 M0 链腾出 GPU 起 S1。
## 5.34 S1 冒烟的教训：`shaping-w-tier` 会盖掉势函数塑形（已修）

第一次 3 分钟冒烟（`1132585`）证明塑形**能跑**（`shaping_calls 127,533`、
`shaping_gamma_aligned true`、开销 8.3%、无非有限值），但两个数字异常：

| 指标 | 冒烟读数 | 应有量级 |
|---|---:|---|
| `reward_shaping_abs_max` | **45.09** | ≤ 0.1 |
| `adv_std` | **16.23** | ~0.2 |

原因：`shaping-w-tier` 默认 **0.5**，把 `shaping_tier_bonus` 表（`0,0,20,60,150,400,900`）
混进了塑形项——那张表最高 900，直接压过 `log_strength` 的势函数（Φ∈[0,1]，λ=0.1）。
**这会把"势函数塑形"变成"隐式 tier 奖励"，也就是被打穿过好几次的那个东西。**

修法（`config/league-entry-s1.json`）：`shaping-w-str 1.0` + **`shaping-w-tier 0.0`**，
只留 `Φ = log1p(Σ)/log1p(30000)` 一项；此时单局塑形总和 = `0.1·ΔΦ ≤ 0.1`，
与名次效用（±1）相比是小量，符合"锐化信用分配、不替换目标"的设计。

**开跑 S1 时的硬性检查（第一轮就看）**：`reward_shaping_abs_max ≤ 1` 且 `adv_std ≤ 1`；
不满足立刻停——说明又混进了别的奖励项，不能当"跑起来了"。

（另注：短冒烟末尾会因 `latest.json` 未产出而 FAILED，这是 `snapshot-every 5` 的正常现象，
不是塑形的问题；正式段按 20 分钟跑不会遇到。）
