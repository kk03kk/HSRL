## 3. 三个能站住的结论

1. **对手库多样性是真实的提升点**：把战团库从 8k（~60 局）换成 6k（~995 局，
   12,689 行），在**其它一切不变**的情况下，`mean_rank` 从 1.333 回到 **1.177**
   （与 base 完全相同），T10 从 +13% 升到 +14%，T16 从 +7% 升到 **+15%**。
   → D1 是**第一个在名次上不掉分的臂**。这也直接印证"56–60 局会过拟合"。
2. **专家动作模仿（BC）在这个规模下无效**：`bc-coef 0.05` + ≥7k（约 78k 条 / ~200 局）
   让 T14 从 −17%（B3）恶化到 −19%（C1），`mean_rank` 1.333→1.323（噪声内）。
   样本池只有 60 局 ≥8k，本来就是薄信号 —— 与 `tools/report_bc_bank.py` 的盘点一致。
3. **B3 家族的共同缺陷是升本太慢**：B3/C1/D1 的 T12 平均 tier 是 4.33/4.51/4.64，
   而 base 5.36、真人 5.78。它们靠"多买人"把 T10 做大（+13~14%），但等级上不去，
   T13–T14 就被反超（每格强度封顶）。**这正是 `tier-target` 想解决的事**，只是上一代
   配方（无门控 + anchor 0.02）把它变成了"只升本不买人"。

## 6.5 一个必须先说清的尺度问题（2026-11-13 05:40）

至今所有臂都是 **6 段 × 20 min ≈ 100–210 轮**的微实验，而 champion
`league-final-14858` 来自 **36 小时联赛、5,316 条 history**。也就是说：

> 用 2 小时的 fork 去"显著超过"一个 36 小时的同源模型，本来就不现实。

**微实验的用途只能是"筛配方"，不是"出成果"**。因此流程应当是：

1. 用这批微实验（D1 的 6k 战团库、G5c/G6c/G7 的门控等级奖励、F4c 的 6k 入场库）
   筛出**唯一一条**最不坏的配方组合；
2. 然后用它开一次**长训**（≥ 12 h，`HSAI_LE_SEGMENTS=36 HSAI_LE_MINUTES=20`
   或 `24×60`），跑满再判；
3. 长训期间只做**评测侧**改动（`workflows/eval_human_gap.py`、`tools/`），
   绝不碰 digest。

这条也解释了为什么"D1 名次不掉"值得重视：它是唯一一个**没有把 champion 变差**的
fork，正是长训的合适起点。

**长训的确切命令模板**（`gpu` 分区 MaxTime 只有 3 h，12 h 必须走 `gpu-long`，
命令行覆盖 sbatch 头里的 partition/time）：

```bash
# 注意：--export 的值必须写在一行里（不能折行、不能用 shell 变量，见 D-038）
sbatch --partition=gpu-long --gres=gpu:h100-47:1 --cpus-per-task=32 --mem=96G --time=12:00:00 --export=ALL,HSAI_LE_OUT=artifacts/runs/entry-main-YYYYMMDD,HSAI_LE_CONFIG=config/league-entry-RECIPE.json,HSAI_LE_SEGMENTS=36,HSAI_LE_MINUTES=20 deploy/slurm/late_entry.sbatch
```

36 段 × 20 min = 12 h，段间自动 `--resume`；**期间禁止任何 digest 相关推送**（D-037）。
