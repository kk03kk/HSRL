## 0. 一句话结论

**它不是"一个能拿来对战的模型"，而是一个"和我们的观测/动作口径高度同源的权重包"。**
两边的观测向量与动作分解几乎完全一致（见 §3），但**对方没有发布任何代码**，
所以权重本身跑不起来；真正的价值在于**它的条件化设计（46 个流派 token）和训练经验**，
而不是它的权重。直接继续训练与直接接真实游戏都不可行，模拟器互评属于"中等工作量、需先自证"。

## 1. 这个模型究竟是什么【已确认】

### 1.1 文件结构（用 `zipfile` + `pickletools` 免执行方式读取，再用 `torch.load(weights_only=True)` 校验）

- 标准 PyTorch zip 检查点，根键 `bg_release_1113`，93 个条目。
- 顶层键：`format`（= `tg-ckpt-v1`）、`net_config`、`state_dict`（87 个张量）、`meta`。
- **md5 = `6ea4d35fdf436513d315d04fe9cbc3c8`，与 README 公布的一致**；大小 39,145,094 B 也一致。

### 1.2 `meta`（训练来源，权威）

```
stage = ppo          iter = 1000        params = 7,989,372
reward = {kind: util, util: [1.0, 0.2, 0, 0, 0, 0, -0.1, -0.2]}
engine_source_hash = 205739107f78dc5a
required_masks = ["no_cancel_choose=1", "keep_start_board=1 (sell restriction)"]
```

即：**PPO（行为克隆初始化）第 1000 轮**，奖励是"按最终名次的固定效用"，不是名次标量也不是 L(Σ)。

### 1.3 网络结构（从 `state_dict` 形状直接读出）

| `pos` | (125, 352) | 位置嵌入，最多 125 个 token |

### 1.4 代码是否存在【已确认：不存在】

- GitHub 仓库文件树只有两个文件：`LICENSE`、`README.md`（`api.github.com/.../git/trees/main?recursive=1` 实测）。
- HuggingFace 仓库 `siblings` 只有 `.gitattributes`、`LICENSE`、`README.md`、`model.pt`。
- README 自己也写明：**"The network code and the game engine (taverngym) are NOT included; the weights alone cannot be run."**

→ **前向传播、特征抽取、token 拼装、动作解码、掩码语义、"流派 token 怎么喂"，全部缺失。**
权重里的 `net_config` 只给了超参数与 `z_vocab` 名字表，没有计算图。

### 1.5 它在什么环境里训练【已确认 + 推测】

- 引擎哈希 `205739107f78dc5a`，名字叫 **taverngym**；**我们的是 `hsbg_engine` 37.0.2，源码指纹 `c4c71014e3d41760`** —— 不是同一个构建【已确认】。
- 卡池 3984（含 padding）→ 3983 张真实卡；**我们 `engine/crates/hsbg-engine/data/cards.json` 恰好 3,983 张**【已确认】。
- 【推测】两者极可能同源（同一份卡表快照 + 同一套观测 schema，见 §3），只是引擎版本/规则补丁不同。

| 观测分解 | — | 68 + 7×31 + 10×40 + 8×40 + 16×40 + 7×9 + 7×7×31 = **3227** | **逐项对得上** |

| 卡表示 | id 嵌入(352) + 311 维属性 → 相加 | id 嵌入(48) + 静态 66 维投影 + 规则文本 64 维哈希投影 → 48→384 | 结构类似、**不可互换** |

| 参数量 | 7.99 M | ≈14.8 M（`entity_model.py` 文档注释） | — |
| 动作空间 | 8 标量 + buy/sell/activate/choose/play(×8)/magnetize/move(7) | **245 = 8 + 8 + 7 + 7 + 16 + 10×8 + 10×7 + 7×7** | **分解方式一致** |

| 奖励 | 名次效用 [1,.2,0,0,0,0,−.1,−.2] | 名次线性 1.0→−1.0 + `L(Σ)=log1p(Σ)/log1p(30000)` | 口径不同 |
| 训练 | PPO，**BC 初始化**，iter 1000（stripped） | PPO（sims=0），无 BC 初始化（BC 作为可选辅助项） | 路线相近 |
| 报告成绩 | 内部 exam 库（人类对局派生），256 局×4 seed，**平均名次 3.474**，吃鸡 19.6% | 我们的**真人战团场** 96 局：**平均名次 5.4375**，吃鸡 0 | **不可比**（对手库与协议都不同） |

### 2.1 为什么说"观测同构"是硬证据，不是巧合【已确认的算术】

我们 `obs_std` 的 3227 维，按块拆开正好是

```
global 68 + board 7×31 + hand 10×40 + shop 8×40 + choices 16×40
        + opponents 7×9 + opponent_boards 7×7×31  = 3227
```

而对方网络里**恰好只有 5 个特征投影器，输入维分别是 68 / 31 / 40 / 9 / 31**。
"68/31/40/9/31 同时对上 + 卡表都是 3983 + 动作分解都是 8+pointer" 这三件事同时成立，
基本不可能是独立设计。

### 2.2 动作分解逐一对照

**【已确认】**：我们 245 段的**大小**分别是 8 / 8 / 7 / 7 / 16 / 80 / 70 / 49（读 `entity_model.py` 的 `SEG`），
对方动作头的**输出维度**分别是 8 / 逐槽 / 逐槽 / 逐槽 / 逐项 / 8 / 查询 / 7（读张量形状）。
**【推测】**：下面这张"哪一段对哪个头"的对应表——数字吻合，但对应关系是我按语义推的，
需要对方的解码代码才能确认。

| 段 | 我们的 245 段区间 | 大小 | 对方对应头 |
|---|---|---|---|
| 标量（EndTurn/Refresh/Freeze/Upgrade/HeroPower×2/DarkGift/Cancel） | 0–7 | 8 | `h_global`(8) |
| Buy | 8–15 | 8 = N_SHOP | `h_buy` 逐槽打分 |
| Sell | 16–22 | 7 = N_BOARD | `h_sell` 逐槽 |
| Activate | 23–29 | 7 | `h_activate` 逐槽 |
| Choose | 30–45 | 16 = N_CHOICE | `h_choose` 逐项 |
| Play | 46–125 | 80 = 10 手牌 × 8 | `h_play`(8) × 手牌 token |
| Magnetize | 126–195 | 70 = 10 × 7 | `q_mag`(手牌→战团) |
| Move | 196–244 | 49 = 7 × 7 | `h_move`(7)（源→目的） |

**结论：动作语义几乎可以 1:1 对应**。这比"都用 PPO"强得多——它意味着**互评的适配层是可控的**，
但要写出来，仍必须猜对 §2.3 的东西。

### 2.3 仍然缺什么（这是所有"能不能跑"问题的关键）【未验证】

1. **token 拼装顺序**：他们 `pos` 是 125，我们的 token 数是 49（1+7+10+8+16+7）——多出来的
   76 个位置怎么用（是否把对手战团展开成 49 个 token、是否按 8 个座位展开）**未知**。
2. **流派 token 怎么注入**：`z_global`(352,46) 是把 one-hot 投到 d 后加到哪个 token？
   `zcard`(46,3984,3) 是加到卡嵌入、还是作为 attention bias？**未知**。
3. **特征是否做 symlog**：我们的模型对输入做 `sign·log1p(|x|)`；他们**没有 norm 统计量**
   （被 stripped），很可能也用 symlog，但**未验证**。
4. **特征块内部的列序**是否与我们 `obs_std` 完全一致（同为 31 维不等于同序）。
5. **掩码语义**：`no_cancel_choose`、`keep_start_board` 在他们的实现里到底屏蔽哪些索引。

## 3. 三个用途的可行性判定

### 3.1 真实游戏接入 —— **基本不可行（除非对方给代码）**

理由（都是硬约束，不是工程量问题）：

1. 我们的实机链路 `client/hsrl_agent/live/*` 是为**我们自己的观测与 245 动作**写的
   （感知 → `encoding` → 3227/124 → `policy` → 245 索引 → 操作序列）。要用对方模型，
   必须在链路里插入"我们 obs → 他们特征块 → 他们 forward → 他们的分头打分 → 245 索引"
   这么一层，而**他们 forward 的规范不存在**。
2. 他们的 `attr`(311) 与我们的 `card_static`(66) 是两套属性编码，卡 id 索引顺序未验证一致；
   实机上错一张卡就是错一整局。
3. 他们的引擎哈希与我们不同 → **卡池/规则补丁可能不同**，实机是活的游戏版本，
   这点无法靠适配层弥补。

**若对方开源 network code**：工作量会降到"写一个 adapter + 校验 245 对应"（约 1–2 天）。

### 3.2 模拟器测评 / 纳入 Elo —— **需要适配，工作量中等，且必须先"自证"**

- 结构上是可行的：我们的评测入口是 `PPOEvaluator.__call__(features, cards, mask, seat) -> (prior[245], value)`
  与 `Policy` 接口，任何"能输出 245 维 masked 分布"的东西都能塞进去。
- 但**必须先把 §2.3 的 5 个未知项用假设补齐**，然后做一次**自证**：
  用他们自己的 `z_vocab` 挑几个流派，在我们 6k 真人战团场跑 256 局，
  看能不能接近他们报告的 3.474 平均名次。**达不到就说明适配错了，互评结果不可信。**
- 我的判断【推测】：拿到对方的成绩量级是可能的（同源 schema），但**没有自证就不该进 Elo 榜**。
- 附带风险：**许可证是 CC BY-NC 4.0（禁止商业使用、必须署名）**，纳入我们内部榜单没问题，
  但不能作为对外发布物的一部分。

### 3.3 继续训练（加载权重）—— **不可行，且不建议**

- **形状不匹配**：d 352→384、4 层→8 层、卡表示 352→48+66+64。没有"直接加载"这回事。
- 迁移学习只剩两条路：
  (a) **蒸馏**：需要先能跑他们的网络（同 3.2 的阻塞）；
  (b) **把他们的卡嵌入 / `zcard` 当作先验**：`zcard` 是 46×3984×3，可映射到我们的
      `archetype_bias`（我们已有按流派的卡偏好表），**这是唯一不依赖 forward 的迁移方式**。
- 另外它已经训练到 iter 1000（8M 参数、4 层），规模比我们小；把它当"更好的初始化"
  没有依据——**他们的成绩口径与我们的不可比**。

### 3.4 其他价值（我认为这才是主要价值）

1. **流派条件化 token（z）**：我们有"推理期软偏置"，他们是**训练期学出来的条件策略**。
   这正好能解决我们当前最痛的问题（§5.14：模型只会拼满一个 B 级阵容，覆盖度上不去靠奖励硬撬）。
   **可以直接借思想、不需要借权重**。
2. **`zcard`(46×3984×3)**：与我们 `config/strategy_cards.json`（33 个流派的核心卡）互补——
   他们是"每张卡在每个流派下的 3 维偏好"，我们是"每个流派的核心卡清单"。
3. **两条"必需掩码"的经验数据**：他们实测 `no_cancel_choose=1` + `keep_start_board=1`
   能改善 0.10–0.14 名。我们已有 `forbid-cancel`，但**没有 `keep_start_board`
   （禁止卖掉开局战团）**，这是一个**低成本、可当场验证**的收益点。
4. **协议对照物**：他们的 exam 库（人类对局派生、8 席）与我们 6k/8k 真人战团场是同一类东西，
   可参考他们"256 局 × 4 seed"的样本量设定（我们目前只用 96 局，SE≈0.25）。

## 4. 最终建议（按我自己的优先级排序）

### 4.1 最推荐：三天内可落地、不需要对方代码的两件事

1. **`keep_start_board` 等价开关**（禁止在 T≤X 卖掉开局/首回合战团）：
   对方实测 +0.10~0.14 名，我们的实现在 `ppo.py` 的 `move_guard`/`forbid_cancel` 旁边加一个
   mask 规则即可。**先在模拟器真人战团场用 96 局验证，成本最低、收益可测。**
2. **流派条件化（z）设计迁移**：把 `config/strategy_cards.json` 的 33 个流派做成我们的
   z-vocab，训练时随机/按局面指定目标流派，让策略学会"给我说目标，我按目标拼"。
   这直接对应我们"覆盖度上不去、只会拼 B 级阵容"的病灶，而且**只用我们自己的数据**。

### 4.2 次推荐：需要适配、建议先做可行性验证

3. **模拟器互评（1–2 天）**：写一个 forward 复现（按 §1.3 的形状 + §2.3 的假设），
   在我们 6k 真人战团场跑 256 局，**拿"能否复现 3.474 量级"当验收门**。
   过了这道门，才能把它当 Elo 榜上的"外部基准"；过不了就说明我们的假设错了，及时止损。

### 4.3 明确不建议

4. **直接加载权重继续训练**（形状不兼容，收益无依据）。
5. **接真实游戏**（缺 forward + 缺特征规范 + 引擎/补丁可能不同；且我们实机链路是围绕
   245 动作写的，风险远大于收益）。

### 4.4 需要你（用户）决定的两件事

- **要不要我去要一份代码**：如果群友愿意给出 network code（哪怕只有 forward + feature builder），
  上面的"互评/蒸馏/接实机"全部从"中等工作量 + 有风险"变成"低风险可做"。
- **许可证**：CC BY-NC 4.0。我们内部研究用没问题，但**如果你以后想把模型/榜单对外发布，
  不能把它的权重或衍生权重打包进去**。

## 5. 事实 / 推测 / 未验证 清单（便于复核）

**【已确认】**
- `model.pt` 的 md5、大小、根键、`state_dict` 全部张量形状、`meta` 字段、`net_config`（含 `z_vocab` 46 项）。
- 对方 GitHub 仓库只有 LICENSE+README；HF 只有 4 个文件 → **无代码、无引擎**。
- 我们 `cards.json` = 3983 张卡；我们模型卡分类 = 3983（代码注释）。
- 我们 `obs_std` 的 3227 维 = 68 + 7×31 + 10×40 + 8×40 + 16×40 + 7×9 + 7×7×31。
- 我们 245 动作 = 8 + 8 + 7 + 7 + 16 + 80 + 70 + 49，与对方 8 个动作头一一对应。
- 我们模型 d=384/8 层（`build_entity_net` 默认值），HC 卡表示 48/66/64。
- 双方引擎源码哈希不同（`c4c71014e3d41760` vs `205739107f78dc5a`）。

**【合理推测】**
- 两个项目同一设计谱系（TavernAgent/AutoTavern），观测与动作 schema 同源。
- 他们的 `attr`(311) 与我们 `card_static`(66) 是同一套卡牌的两种编码。
- 他们报告 3.474 与我们的 5.44 不可比（对手库、席位数、协议都不同）。

**【未验证】**
- token 顺序/125 个位置怎么填、z 与 zcard 注入点、是否 symlog、掩码具体索引、
  卡 id 索引顺序是否逐位一致、他们引擎的规则补丁是否与我们一致。
- 复现他们成绩所需的适配精度（这是 4.2 那道"自证门"要回答的问题）。
