# 模块 1：模拟器规则一致性与补丁验收

2026-11-21。对象为 3286 使用的 Player150 冻结版。核查了发布身份、两个补丁条目、一个已知行为差异，以及真人战团库实际验证的字段。

## 当前版本与实现

- 主检出为 37.0.2 基线，构建指纹 `c4c71014e3d41760`。现役 Player150 用 37.0.2.256589 基础卡表叠加 37.0.3 服务端规则，Windows 实测构建 `8bd1f4785018c474`，NUS 冻结源码为 `cb9587ac0cfa4b1875415277652392043a43e082`。暴雪说明 37.0.3 于 11 月 17 日作为服务端热修上线。单看客户端 build 不能识别这种变更。[官方热修](https://us.forums.blizzard.com/en/hearthstone/t/3703-hotfix-patch/168317)
- `engine/crates/hsbg-engine/data/cards.json` 编译进 Rust 二进制，固定 ID 顺序、卡面、数值、关键字和候选池元数据。`content/*.rs` 通过 `script.rs` 注册战吼、亡语、光环和其他钩子。规则改动可能需要同时修改卡文、事件逻辑以及市场或发现过滤。缺少脚本的效果应单独登记。默认 `Implemented` 排除未实现的效果牌，`AllVanilla` 会让此类卡只保留数值和关键字。
- `engine.rs` 管八席、牌池、实体与随机状态。`actions.rs` 产生合法掩码并分发动作，`recruit.rs` 处理经济、上场、目标、挂起选项和连锁，`flow.rs` 推进回合。`combat.rs` 用战团副本结算攻击、死亡和复生，另把永久效果写回玩家状态。相同规则配置、种子和动作序列用于内部确定性回放。
- `hsbg-engine-py/src/lib.rs` 暴露 `Game.legal_mask`、`Game.step`、`Game.observe` 与批量接口。原生为 245 动作、3,227 浮点、124 卡槽。Player150 加到 4,967 浮点，并使用 150 步预算。这些模型输入和实验预算需独立验收。[训练与部署身份](PLAYER150_FIVE_20261120.md) · [模块架构](../ARCHITECTURE.md)

### 一个已有差异与一个高优先级待确认项

- 暴雪已知问题清单写明 Talent Scout（`BG25_HERO_105_Buddy`）在没有其他伙伴时无法出牌。用现役二进制、种子 `3703001` 进入招募，清空该席手牌、商店和战团，场上放非伙伴 `BGS_039`，手牌仅放 Talent Scout。动作 47 `Play { hand: 0, pos: 1 }` 在合法掩码中开放，执行后盘面从 1 到 2、手牌从 1 到 0，且无待选目标。冻结版 `tests/mechanics.rs::talent_scout_and_baby_nzoth_make_the_chosen_minion_golden` 也锁定这个行为。此处已确认模拟器和官方记录有差异，当前游戏会话的直接复现及它在训练中的触发频率待确认。[暴雪已知问题](https://us.forums.blizzard.com/en/hearthstone/t/370-highlights-known-issues/153567)
- 冻结版 `combat.rs::first_attacker` 在随从等量时让高酒馆等级方先手，等级也相同时才抽签。37.0.3 实机是否使用此破平规则待确认。优先从版本可辨、双方随从等量且等级不同的原始战斗事件抽样，剔除战斗开始技能和额外攻击。记录首个正常攻击者、双方酒馆等级、双方战斗开场前后随从数量。

## 新补丁的验收顺序

1. **登记变更。** 记录公告、热修生效时间、禁用和已知问题，分别记客户端 build、基础卡表、服务端规则。给每条变更写期望前置状态、动作、结算和来源。已知线上异常与设计预期分别标识，按实际研究目标选择规则版本。[补丁公告](https://hearthstone.blizzard.com/en-us/news/patchnotes) · [热修与禁用线索](https://us.forums.blizzard.com/en/hearthstone/t/370-highlights-known-issues/153567)
2. **隔离实现。** 从已验收版本开分支。卡面、费用、星级、入池与禁用核对卡表和配置；触发、候选筛选、目标与行动语义核对 Rust 逻辑。热修优先保留 ID 和编号，移出卡池时保留历史 ID。每条变化补普通与金色、正例与反例及相邻边界测试，涉及阶段再加跨回合用例。
3. **分层测试。** 在计算节点跑 Rust 回归并构建独立 wheel，Windows 验证目标二进制。再取同版本原始 `Power.log` 或 Firestone 记录，按“可见前态 → 实际动作或事件 → 可见后态”比对金币、牌区、候选、附着、触发顺序和战斗结果。确定性字段逐项匹配。服务器随机种子不可见时，按日志已观察到的随机分支核对后续事件，或在同类局面上比较分布，报告样本量。未知字段标待确认。单独报告规则覆盖率、差异和样本缺失。
4. **冻结发布与重新立基线。** 用新发布和新环境保存引擎源码锁、构建指纹、wheel、卡表、词表、动作语义、观测与快照 schema。动作或输入语义改变时，逐项验证旧权重和 Trainer 的兼容性。重建或重新验证同版本训练与留出库，用同一新协议跑旧模型基线。旧快照可能带有补丁前积累的身材或经济，不并入新场。保留旧资产和协议。[冻结发布运维](../ENGINEERING.md) · [既有 37.0.3 迁移记录](PEER_R1_LIVE_PARITY_20261120.md)
5. **单独判断上线。** 一旦改动触及客户端 build、可用动作、目标落点或回执，补 Windows Doctor、历史快照回放和独立的真实动作验收。规则验证、模型棋力与实机执行分别记录。此次只做只读核查和本机离线探针。
