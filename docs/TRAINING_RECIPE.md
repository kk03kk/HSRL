## 1. 参照物：AutoTavern 论文 Table 7

论文：Build, Don't Play（AutoTavern），[arXiv:2610.33845](https://arxiv.org/html/2610.33845v1)，§6 Model and training。

论文原文要点：
- PPO，**每轮约 100 万决策**，奖励是**终局名次效用**；
- **一个 stage = 300 轮 ≈ 3.1 亿决策（57 万局）**，每个 stage 从上一个 stage 继续，并带 **KL anchor**；
- 网络 entity transformer，d=384 / 8 层 / 8 头 / 约 18M 参数；
- 算力：8×H200 + 128 CPU 核。

Table 7 超参（本仓库对齐记录见 `records/source-docs/hsbg/docs/MULTISTAGE_TRAINING.md` §12）：

```
lr 6e-06 → 5e-06        有效 minibatch 8192（微批 1024 × 梯度累积 8）
clip 0.2                target-KL 0.05
lambda 0.995            entropy-coef 0.002
grad-clip 1.0           KL anchor β=0.1，仅前 100 轮
sims 0（不做搜索）
```

### 2.3 对手场（本项目唯一被验证有效的难度杠杆）

| 项 | 值 | 依据 |
|---|---|---|
| 快照库（训练） | `artifacts/libraries/arena-cal-v4-snap` | 1,534 帧，覆盖 turn 1–18；**按候选 `arena_v3` 的战力曲线校准**（v3 是按旧冠军校准的） |
| 快照库（考试，held-out） | `artifacts/libraries/arena-cal-v4hold-snap` | 源自 `eval-m6k.jsonl`（与训练池不同源），**只用于判胜** |
| 注入席位 | `--mirror-seats 7 --mirror-p 1` | 7 个非 learner 席位全部注入 |
| 采样 | `--mirror-sample p50band` | 分位带 0.45–0.55 内均匀取样：同一难度目标 + 恢复对手多样性 |
| 严格模式 | `--mirror-strict 0` | 缺帧时回退引擎 bot（库只有 seat 0，靠跨席回退） |
| 回合上限 | `--mirror-max-turn 0` | 不限 |
| 人类战团 / 入场课程 | 全关（`--human-board-p 0 --entry-p 0`） | 本轮不启用 |

**校准系数（`build_arena_library.py` 的 `DEFAULT_MULT`，v4 = 2026-11-14 第二轮）**：
前期（1–7 回合）**0.82**（v1–v3 是 0.85，再降一点）/ 第 8 回合 0.88 / **第 9 回合 1.00** /
10–18 回合 **1.08 → 1.22**（v1–v3 是 1.05 → 1.15，整体往上拉）。
含义：前期对手略弱于模型（鼓励升本），第 9 回合势均力敌，后期只比模型强一点点且缓慢上升，**绝不出现一个回合跳好几倍**。
系数是**相对"当前模型该回合中位战力"**的，所以换模型后必须重建库 —— v4 就是按候选 `arena_v3` 的曲线重建的。

> 每次换冠军后，**必须基于新冠军的战力曲线重新建库**，这是迭代流程的一部分。

### 2.6 奖励

奖励 = **终局名次效用**（唯一的值函数目标）+ **一个小的升本节奏项**。

**v4 版（2026-11-14 第二轮，用户要求"在不妨碍名次奖励的前提下尽量加"）**：

| 参数 | v4 值 | v3 旧值 | 依据 |
|---|---|---|---|
| `--tier-target-coef` | **1.0** | 0.25 | 4× |
| `--tier-bonus`（命中） | **0.20** → 实际 **+0.20** | 0.15 → +0.0375 | |
| `--tier-penalty`（落空） | **0.15** → 实际 **−0.15** | 0.10 → −0.025 | |
| 目标表 | **`8:5,11:5,14:6`** | `2:2,5:3,7:4,8:5` | 旧表第 9 回合后**没有任何检查点**；且 T2/T5/T7 在 90% 的局里都命中（等于白送分） |
| 板面门控 | `--tier-gate-k 0.75`，ref **`8:150,11:850,14:1400`** | `2:1,5:30,7:100,8:150` | **表里每个 turn 都必须有 ref**，缺 ref 会被无条件挡掉 |
| 其余塑形 | 全 0 | 同 | |

**命中率与量级（按候选实测 tier 直方图算）**：T8 要求 5 本 → 命中 30%；T11 要求 5 本 → 36%；T14 要求 6 本 → 12%。
每局期望 **−0.177**（名次全距 2.0 的 **8.9%**），旧版 −0.048（2.4%）⇒ **压力约 3.7 倍**。
单局区间 [−0.45, +0.60]：最坏情形占全距 22.5%，仍明显小于名次信号 ±1.0。全程约 1,350 次检查（3 档 × 512 局 − 门控挡掉）。

> **2026-11-14 第一轮的教训**：旧版 302 轮跑完后候选 tier 反而比冠军低 0.5~0.7，且**第 9 回合之后完全没约束** ——
> 奖励加了等于没加。所以 v4 的核心不是"把系数加大"，而是**把检查点铺到第 14 回合**，并且只留有约束力的档位。

> **与论文的已知差异 #2**：论文只有终局名次效用，没有塑形项。用户 2026-11-14 决定保留该项做实验。
> **门控是这条奖励的安全阀**：2026-11-13 实测过"只看 tier 的奖励会被'把金币全砸升级、不买随从'打穿"（板面 −33%）。

### 2.7 冻结契约（改它需要用户明确授权）

`--max-actions-per-turn 80`、`--move-guard 1 --move-cap 5 --move-repeat-limit 2`、`--forbid-cancel 1`、`--forbid-unfreeze 1`、`--sims 0`。

## 3. 规模口径（不要混用"轮"这个字）

| 单位 | 论文 | 我们 |
|---|---|---|
| 一轮 | ≈100 万决策 | ≈12.4 万决策（512 局） |
| 一个 stage | 300 轮 = 3.1 亿决策 | — |
| 一次 3 小时作业（165 分钟训练） | — | **实测约 300 轮 ≈ 3,700 万决策 ≈ 论文一个 stage 的 1/8** |

> **注意：流水线可能被一次 KL 尖峰永久打回串行。**
> 2026-11-14 那次运行实测：第 0–15 轮重叠正常（**19.5 s/轮**）；第 15→16 轮出现一次瞬时
> KL=0.091 触发 `target-KL 0.05` 早停 → 该轮几乎零更新 → `--pipeline-zero-step-fallback 1`
> 判定"旧批次零更新"，**之后永久改为串行采集**（**31.9 s/轮**，吞吐 −39%），而 KL 下一轮就
> 回落到 0.0024 也没恢复。
> 影响：**只影响这一个作业能跑多少轮，不影响更新质量**（每轮仍 15–16 步）。
> 估轮数时要用 ~32 s/轮，不要用 19.5 s/轮。

**所以一次 3 小时作业不是"训练完成"，而是"论文尺度下一个 stage 的一小部分"。** 要"变强"需要多轮累积。

## 4. 吞吐基线（用于判断作业是否健康）

| 场景 | 采集速率 | 每轮墙钟 | 备注 |
|---|---|---|---|
| 单卡 47GB（learner 与采集共用） | 5,900 决策/秒 | ~55 s | v2 实测 |
| **双卡分卡 + 流水线重叠正常** | **8,200–9,100 决策/秒** | **~19.5 s** | 2026-11-14 第 0–15 轮实测 |
| **双卡分卡 + 被打回串行** | 同上 | **~31.9 s** | 同一次运行第 16 轮之后（见 §3 的 KL 尖峰说明） |
| 论文字面 | — | — | 8×H200 + 128 核，不可比 |

采集速率（`decisions_per_s`）**不随串行/并行变化**，变的是每轮总墙钟——因为串行时 collect 与 ppo 不再重叠。

每轮 PPO 优化步数应为 **15–16**（= 有效批 8,192 生效）。若日志里出现 ~124 步，说明 `--grad-accum` 没生效。

## 6. 本站 GPU 事实（2026-11-14 实测，踩过坑）

- `h100-47` 不是整卡，是 **MIG 3g.47gb 切片（46.4 GiB）**。
- 一次分配 2 张切片时，两张可能落在**同一张物理卡**上 → `torch.cuda.device_count()==1` → `--gpus 1` 越界崩溃。
- 也可能分属两张物理卡 → `device_count()==2`，此时才是真双卡。
- 脚本因此内置**双卡硬门禁**：`device_count < 2` 就在建目录前 `exit 3`，由外部重投换节点（约 1 分钟一轮）。
- 账号 QOS（`normal`）按用户上限：`h100-47=2`、`h100-96=1`、`a100-80=1`、`a100-40=2`、`nv=8`、`gres/gpu=8`。
  **"两张整卡 H100"这个账号拿不到**（整卡上限 1 张）。
- `nv` 类型是 TITAN V 11.8 GiB，太弱，不用于训练。

## 7. 与冠军那套配方的差异（为什么会不同）

冠军（`league-36h`，2026-11-11）用的是 `personal.py` + `config/league-36h.json`，实际生效 `lr≈1.667e-06`（被 trainer state 的 `base_lrs` 覆盖）、有效批 1,024、anchor 250 轮。本配方按论文 Table 7 重新对齐，**因此与冠军那条不是同一套超参**，两者不能按"同配方"直接比吞吐。
